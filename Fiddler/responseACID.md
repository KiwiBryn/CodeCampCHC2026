You: explain the database term ACIDMistral: **ACID** is a fundamental set of properties that ensure **reliable transactions** in database systems. It stands for:1. **Atomicity**2. **Consistency**3. **Isolation**4. **Durability**These properties guarantee that database operations are executed correctly and safely, even in the face of failures or concurrent access.---### **1. Atomicity****Definition:** A transaction is treated as a single, indivisible unit of work. Either **all** operations in the transaction are completed successfully, or **none** are.**Example:**- Transferring money from Account A to Account B involves two steps:  - **Debit Account A** (subtract amount)  - **Credit Account B** (add amount)- If the system crashes after debiting but before crediting, **Atomicity** ensures the transaction fails, and the money is returned to Account A.**How it works:**- The database uses **commit** (success) or **rollback** (failure) mechanisms.- If any part of the transaction fails, the entire transaction is undone.---### **2. Consistency****Definition:** A transaction brings the database from one **valid state** to another, adhering to predefined rules (e.g., constraints, triggers, or business logic).**Example:**- A database rule states: *"Account balance cannot be negative."*- If a transaction tries to withdraw more than the balance, **Consistency** prevents it, ensuring the database remains in a valid state.**How it works:**- Constraints (e.g., `NOT NULL`, `UNIQUE`, `FOREIGN KEY`) and triggers enforce rules.- If a transaction violates these rules, it fails (violating **Atomicity**).---### **3. Isolation****Definition:** Concurrent transactions execute independently without interfering with each other, ensuring each transaction sees a **consistent view** of the database.**Example:**- Two users try to update the same bank account simultaneously.- Without **Isolation**, one user might see the other's uncommitted changes, leading to incorrect results.- **Isolation** ensures each transaction works on a **snapshot** of the database until it commits.**Isolation Levels (from strongest to weakest):**| Level          | Description                                                                 | Example Risk                          ||----------------|-----------------------------------------------------------------------------|----------------------------------------|| **Serializable** | Highest isolation; prevents all anomalies (most restrictive).          | Performance overhead.                  || **Repeatable Read** | Prevents dirty reads and non-repeatable reads.                          | Phantom reads possible.                || **Read Committed** | Prevents dirty reads (but allows non-repeatable reads).                 | Dirty reads (reading uncommitted data).|| **Read Uncommitted** | Lowest isolation; allows dirty reads (fastest but least safe).       | Dirty reads, non-repeatable reads.      |**Common Anomalies (without proper Isolation):**- **Dirty Read:** Reading uncommitted data (e.g., seeing a transaction that later rolls back).- **Non-Repeatable Read:** A transaction reads the same row twice and gets different results.- **Phantom Read:** A transaction re-runs and finds new rows that weren't there before (e.g., new records inserted by another transaction).---### **4. Durability****Definition:** Once a transaction is **committed**, it remains committed even in the event of a system failure (e.g., crash, power outage).**Example:**- You transfer $100 from Account A to Account B.- The transaction commits, but the server crashes before writing to disk.- **Durability** ensures the changes are **permanently stored** (e.g., via **write-ahead logging** or **transaction logs**).**How it works:**- Databases use **transaction logs** (or **redo logs**) to record changes before applying them to the database.- On recovery, the database replays the log to restore consistency.---### **ACID in Real-World Databases**| Database       | ACID Compliance | Notes High reliability.                | Scalability over consistency. || Slower for high write loads.     | Optimized for distributed systems. || Examples: PostgreSQL, MySQL.     | Examples: Cassandra, transactions (banking). | High write scalability (e.g., IoT sensors). || Inventory management.            | Social media feeds (eventual consistency is acceptable). || E-commerce order processing.      | Real-time analytics (where freshness > perfection). || Critical data integrity is required. | Distributed systems where partition tolerance is prioritized. |---### **Summary**| Property      | Meaning                                                                 | Example Impact                          ||---------------|--------------------------------------------------------------------------|------------------------------------------|| **Atomicity** | All-or-nothing execution.                                                | Prevents partial updates.                || **Consistency** | Database rules are always followed.                                      | No invalid data (e.g., negative balances). || **Isolation**  | Transactions don't interfere.                                           | Prevents dirty reads, phantom reads.     || **Durability** | Committed changes survive failures.                                     | Recovery after crashes.                  |ACID ensures **data integrity** in traditional databases, while **BASE** (used in NoSQL) prioritizes **scalability** and **availability** over strict consistency.
